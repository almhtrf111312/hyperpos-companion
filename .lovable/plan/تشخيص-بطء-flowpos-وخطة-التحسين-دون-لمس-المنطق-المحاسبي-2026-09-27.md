# تشخيص بطء FlowPOS وخطة التحسين (دون لمس المنطق المحاسبي)

## أ. السبب الحقيقي للبطء (مؤكد بالفحص)
1. **N+1 في الفواتير** — `src/lib/cloud/invoices-cloud.ts` (سطر 287-310): بعد جلب كل الفواتير، يُرسل طلب منفصل لكل فاتورة لجلب أصنافها. 40 فاتورة = 41 طلبًا، و5,000 فاتورة = 5,001 طلب. هذا هو السبب الأول لتأخر 10-20 ثانية.
2. **لا يوجد فهرس على `invoice_items.invoice_id`** في قاعدة البيانات (تم التحقق من الفهارس)، فكل طلب من الطلبات السابقة يفحص جدول الأصناف كاملًا.
3. **تحميل كل السجلات دفعة واحدة** — الفواتير والديون والمنتجات والمصروفات تُجلب كاملة بـ `select('*')` دون Pagination (`fetchFromSupabase` بلا حد).
4. **Dashboard يحسب على الجهاز** — `src/pages/Dashboard.tsx` سطر 85 يجلب كل الفواتير والمنتجات والشركاء والمصروفات والديون والمشتريات ثم يجمعها محليًا؛ القيم تبدأ من 0 قبل انتهاء التحميل.
5. **إعادة تحميل شاملة** — `use-realtime-sync.tsx` يمسح كل الـ Cache ويرسل أحداث تحديث لكل الجداول عند الاشتراك وعند عودة الاتصال، وأي تغيير في سجل واحد يعيد تحميل القائمة كلها.
6. **فهارس ناقصة** على `debts(status)`, `customers(phone)`, `invoices(created_at)`, `invoices(customer_id)`.

## ب. زر مسح البحث في التقارير
`ReportFiltersBar.tsx` يحوي زر «مسح الفلاتر» فقط (يمسح كل شيء)، ولا يوجد زر مسح داخل مربع البحث نفسه. سيُضاف زر X داخل الحقل يمسح النص فقط، بمساحة لمس 44px ودعم RTL.

## ج. دراسة الاقتراحات — التصنيف
| الاقتراح | التصنيف |
|---|---|
| إزالة N+1 بجلب الأصناف دفعة واحدة `.in('invoice_id', ids)` | آمن |
| فهارس جديدة | آمن (Migration بسيط، قابل للتراجع) |
| Pagination للفواتير/الديون + تحميل التفاصيل عند الفتح | آمن بشروط (الإجماليات تبقى من الخادم) |
| Skeleton وحالات تحميل بدل الصفر في Dashboard | آمن |
| عرض آخر نسخة محلية فورًا مع وقت آخر مزامنة | آمن بشروط (لا تُستخدم للعمليات المالية) |
| تحديث السجل المتغير فقط من Realtime | آمن |
| نقل حسابات Dashboard إلى RPC على الخادم | **FINANCIAL LOGIC IMPACT — موافقة مطلوبة** (إعادة كتابة صيغ الربح بـ SQL) — مؤجَّل |
| مزامنة تفاضلية كاملة بـ updated_at | تحتاج تجربة محدودة — مرحلة لاحقة |

لا يمس أي بند في المرحلتين 1 و2 المبيعات أو الديون أو المرتجعات أو المخزون أو الصندوق أو الـ RPCs المالية.

## و. الخطة المرحلية

**المرحلة 1 — تحسينات آمنة سريعة (تنفذ الآن)**
- استبدال N+1 بطلب واحد (أو دفعات من 200 معرّف) لأصناف الفواتير.
- Dashboard: حالات `loading/success/error/stale` لكل بطاقة، Skeleton و«جارٍ الحساب...» بدل 0، زر إعادة المحاولة، وعرض آخر قيم محفوظة مع وقتها.
- Realtime: إلغاء مسح كل الـ Cache عند الاشتراك إن كان هناك تحديث حديث (<60 ث)، وإطلاق حدث الجدول المتأثر فقط.
- زر مسح داخل مربع بحث التقارير + تكبير المربع.
- مؤشر مزامنة يوضح الحالة (مزامنة / نجحت / بيانات قديمة / خطأ / غير متصل) ووقت آخر مزامنة ناجحة.

**المرحلة 2 — قاعدة البيانات (Migration فهارس فقط)**
- `invoice_items(invoice_id)`, `invoices(user_id, created_at desc)`, `invoices(customer_id)`, `debts(user_id, status)`, `stock_movements(product_id)`.

**المرحلة 3 — Pagination وCache دائم**
- الفواتير والديون: أول 100 سجل مرتبة بالتاريخ + «تحميل المزيد»؛ الديون المفتوحة أولًا.
- حفظ آخر نسخة ناجحة في IndexedDB (مثل المنتجات حاليًا) وعرضها فورًا عند فتح التطبيق.

**المرحلة 4 — مؤجلة وتحتاج موافقتك**
- Aggregation على الخادم للوحة التحكم (FINANCIAL LOGIC IMPACT).
- مزامنة تفاضلية بـ updated_at.
